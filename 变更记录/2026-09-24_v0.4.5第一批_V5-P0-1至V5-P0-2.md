## 三、与文档条款对照说明

### V5-P0-1 → §10.3 托管意图 + §10.2 review 流程

- **§10.3 写入侧安全**：token 一次性、Origin 同源校验——完整保留。do_GET 的 token 改经查询参数传递（与 POST 的 X-Token 同源同 token），do_OPTIONS 仅返回 CORS 头不暴露任何数据。页面由服务端托管后，浏览器打开 `http://127.0.0.1:<port>/review.html?token=<token>` 即同源，fetch `/save` 自动带正确 Origin，原 Origin:null / 无 Origin / OPTIONS 501 三种阻断同时消失。
- **§10.2 review 流程**：原流程在真实浏览器走不通（file:// 打开 → 跨源 403/501）。修复后 main.py 打印完整页面 URL，用户从浏览器打开即同源可用，流程闭环。
- **未改动**：POST 的 Origin 校验逻辑、token 生成与生命周期、BV 正则、manual.json 原子写——均保持不变。

### V5-P0-2 → §4.1 人工回灌永远覆盖铁律

- **§4.1 铁律**：manual.json > whitelist.json > uploaders.json > 评分。修复前 manual 重查 SQL 只查 `status='DONE'`，导致 FAV_FAILED / MATCHED 状态的歌人工回灌新 BV 后静默失效——更糟的是 resume 阶段三（main.py:654-658）直接取库内旧 bvid 收藏，静默收藏错误内容。修复后 SQL 扩为 `status IN ('DONE','MATCHED','FAV_FAILED')`，三种状态一致升级为 MATCHED（正式运行，交阶段三收藏新 BV）或 DONE（dry-run，仅更新 bvid/method）。
- **MANUAL 状态**：manual 重查 SQL 不含 MANUAL，但 MANUAL 歌在 resume 阶段二经 matcher（matcher.py:259 `if key in manual: return self._finish(key, "MANUAL", manual[key])`）直接取 manual BV 无需搜索，终态 MATCHED 交阶段三——与另三种状态殊途同归。
- **未改动**：matcher 的 manual 优先级检查、stage2 跳过逻辑（DONE/MATCHED/FAV_FAILED 跳过）、stage3 查询条件（MATCHED/FAV_FAILED + bvid IS NOT NULL）——均保持不变，升级后的歌曲自然流入既有的阶段三收藏链路。
